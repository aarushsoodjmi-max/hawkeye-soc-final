# HawkEye SOC — Merged Backend: Project Structure

This document describes the result of the **integration/compilation pass**
that merged seven independently developed modules into a single, coherent
FastAPI backend. No business logic, algorithms, or architecture were
rewritten or redesigned — this was a structural merge only.

## Module → Package Mapping

| Input Module (source ZIP)          | Integrated Into      | Notes |
|-------------------------------------|-----------------------|-------|
| FastAPI Skeleton (`hawkeye-soc-backend`) | `app/` (root: `main.py`, `config.py`, `models.py`, `schemas.py`, `routes/`, `services/`) | Used as the base project; unchanged except `main.py` docstring |
| Dataset Engine (`files__2_`)        | `app/data/`            | `generate_dataset.py`, `preprocess.py`, `alerts.csv` — matches the path `app/config.py` already expected (`ALERTS_CSV_PATH`) |
| Correlation Engine (`files__1_`)    | `app/correlation/`      | `correlation_engine.py`, `incident_builder.py`, `timeline.py` |
| ML Module (`files`)                 | `app/ml/`                | `feature_engineering.py`, `train_model.py`, `evaluate.py`, `predictor.py` — path matches the one hardcoded in module docstrings/CLI examples (`backend/app/ml/root_cause_model.pkl`) |
| Analytics (`files__3_`)             | `app/analytics/`          | `metrics.py`, `explainability.py`, `risk_scoring.py` — path matches the one in the module's own docstring |
| Reporting (`files__1___1_`)         | `app/reporting/`           | `report_generator.py`, `executive_summary.py`, `threat_intelligence.py`, `json_export.py`, `sample_reports.py`, plus pre-generated sample output (`output/INC-*.json`) — path matches `sample_reports.py`'s own default output directory |

## Integration Work Performed

1. **Folder merge** — the FastAPI skeleton (`hawkeye-soc-backend/backend`)
   was used as the project root. Each remaining module was placed into its
   own subpackage under `app/`, using the destination path already implied
   by that module's own docstrings/README (e.g. the ML module's CLI help
   text literally reads `backend/app/ml/root_cause_model.pkl`).
2. **`__init__.py` created where required** for packages that didn't already
   have one, so that existing relative imports resolve correctly:
   - `app/data/__init__.py` (Dataset Engine)
   - `app/correlation/__init__.py` (Correlation Engine — required by
     `incident_builder.py`'s `from .correlation_engine import ...`)
   - `app/ml/__init__.py` (ML Module)
   All other modules (Analytics, Reporting, Simulator) already shipped
   their own `__init__.py` and were copied unchanged.
3. **Imports** — no import statements inside any business-logic file were
   rewritten. The ML module's own technique of
   `sys.path.insert(0, str(Path(__file__).parent))` followed by plain local
   imports (e.g. `from feature_engineering import ...`) was left exactly as
   authored; it continues to work unchanged inside `app/ml/`.
4. **Duplicates** — file hashes were compared across all seven source ZIPs;
   no duplicate business-logic files were found, so nothing was removed.
5. **`requirements.txt`** — merged from the FastAPI skeleton's existing file
   plus the additional third-party packages actually imported by the ML
   module (`scikit-learn`, `numpy`, `joblib`). All other modules use only
   the standard library or `pandas` (already listed).
6. **`app/main.py`** — routing is unchanged: it still registers only the
   two routers that existed in the original skeleton (`alerts`, `incidents`).
   No new endpoints were added for the newly merged modules, per the
   "existing routes only" requirement. The docstring was updated to
   reflect that the backend is no longer a bare skeleton.

## Verified Working (integration-only checks — no logic exercised beyond
## calling existing public functions as-is)

- All `.py` files compile (`python -m py_compile`) with no syntax errors.
- All new packages import successfully: `app.data`, `app.correlation`,
  `app.ml`, `app.analytics`, `app.reporting`, `app.simulator`.
- End-to-end smoke test using each module's own public API:
  `app.data.load_dataset()` → `app.data.clean_data()` →
  `app.correlation.correlate_alerts()` → `app.analytics.risk_scoring` ran
  successfully against the shipped `alerts.csv` (1000 rows → 979 correlated
  incidents), confirming the Dataset Engine and Correlation Engine share a
  compatible alert schema.

## Known Integration Note (not fixed — out of scope)

The **Simulator**'s generated alert schema (columns such as `username`,
`scenario`) does not match the **Correlation Engine**'s expected schema
(`user`, `device`, `ip_address`, `alert_type`, `source`, `root_cause`).
Each module's own README describes it as self-contained and independent
of the others, so this is a pre-existing data-contract mismatch between
two independently developed modules — reconciling it would mean altering
one module's business logic/output schema, which is outside the scope of
this compilation task. The Dataset Engine's `alerts.csv` already uses the
schema the Correlation Engine expects, so that pairing works out of the box.
